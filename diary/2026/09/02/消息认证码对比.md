# HMAC 与其他消息认证码对比

消息认证码 MAC（Message Authentication Code）目标统一：**带密钥，提供完整性 + 来源认证**。
大类分为：

1. **基于哈希：HMAC**（TLS1.3、HKDF、JWT 主力）
2. **基于块密码：CMAC‑AES（OMAC1）、CBC‑MAC**
3. **AEAD 内置 MAC：GCM‑GMAC、ChaCha20‑Poly1305（Poly1305 属于通用 MAC）**
4. **通用多项式 MAC：Poly1305**

> 
> 核心区分维度：底层原语、安全假设、性能、密钥需求、是否可直接派生密钥、TLS 实际使用场景。

## 1. HMAC（RFC2104，基于密码哈希 SHA‑256/SHA‑384）

\(HMAC(K,M)=H\left[(K\oplus opad)\Vert H\left((K\oplus ipad)\Vert M\right)\right]\)

**特点**

- 底层：密码学哈希函数，不需要块密码。
- 密钥：单个密钥 K；密钥长度灵活。
- 安全假设：**哈希抗碰撞、抗二次原像**。
- 优点：
  1. 实现成熟，大量标准：TLS HKDF、JWT、OAuth。HKDF 直接构建在 HMAC 之上，**可以做密钥派生**，这是 HMAC 独有的巨大优势。
  2. 流式处理，消息可以增量输入，不需要预先知道完整消息长度。
  3. 哈希软件优化极好，CPU 通用寄存器性能优秀。
- 缺点：
  1. 两轮哈希，计算开销比 Poly1305 更高。
  2. 哈希有固定块大小（SHA‑256 block=64B），短消息也要处理完整块。

> 
> TLS1.3 用途：HKDF 全部原语、Finished 报文 verify_data。
> ⚠️注意：TLS 的 AEAD 加密 (AES‑GCM) 并不使用 HMAC，GCM 自带 GMAC。

## 2. CBC‑MAC（老块密码 MAC，废弃）

基于 AES‑CBC 模式，丢弃密文输出只取最后一个密文块作为 MAC。

- 底层：块密码 AES。
- 致命缺陷：**不安全，消息长度可变时直接攻破**；只定长消息勉强安全。
- 现状：已经被标准废弃，**TLS 不再使用**。

##3. CMAC‑AES（OMAC1，RFC4493）
CBC‑MAC 的安全改良版本，增加两个子密钥处理最后不完整块。

**特点**

- 底层：AES 块密码。
- 需要：1 个 AES 主密钥，内部推导 2 个子密钥。
- 优点：短消息安全，输出等于 AES 块大小 16 字节。
- 缺点：
  1. 只能做 MAC，**不能用来做密钥派生，没有 HKDF 等价物**。
  2. 硬件 AES 加速环境性能好；无 AES 硬件加速时 CPU 开销大。
- 使用场景：IPsec，部分金融；**TLS 不使用 CMAC**。

##4. GMAC（GCM 内置 MAC）
GMAC = Galois Message Authentication Code，是 AES‑GCM 的认证部分。
多项式在 GF (2^128) 运算。

**特点**

- 必须搭配 AES‑GCM AEAD；GMAC 不单独作为独立 MAC 使用。
- 需要：AES 密钥生成哈希子密钥 H；nonce（IV）至关重要。
- 致命约束：**nonce 绝对不能重复**，同一密钥下 nonce 重复直接完全攻破。
- TLS1.3：`TLS_AES_128_GCM_SHA256` 报文的**记录层认证用 GMAC**。

> 
> 区分：
> 
> 
> - 记录层密文完整性：GMAC（AEAD 内置）
> - 握手 Finished verify_data：**HMAC‑SHA256**
> 很多人混淆，TLS1.3 同时存在两套完全不同的 MAC。

##5. Poly1305（RFC7539）
多项式 MAC，搭配 ChaCha20，构成 ChaCha20‑Poly1305 AEAD。

**特点**

- 底层：有限域多项式运算，**不需要哈希、不需要块密码**。
- 每条消息需要**全新的 256 位密钥**；不能复用同一个 Poly1305 密钥多条消息。
- 优点：软件性能极强，无 AES 硬件加速的设备（移动端、物联网）速度远快 HMAC、AES。
- 缺点：
  1. 密钥不能重复使用；**不能用于 HKDF，不能做密钥派生**。
  2. 不是通用可复用密钥的 MAC。
- TLS1.3：`TLS_CHACHA20_POLY1305_SHA256` 记录层认证使用 Poly1305。

> 
> 🎯 TLS1.3 两套 MAC 分工（非常关键）

1. **握手逻辑层（Finished verify_data，HKDF 密钥调度）：HMAC‑SHA256**
   - 需要同一个 secret（traffic_secret）重复对多条 transcript 做认证；需要密钥派生能力，只能选 HMAC。
2. **TLS 记录层，加密报文完整性：GMAC / Poly1305（AEAD 内置 MAC）**
   - 每条记录使用独立 nonce，属于 AEAD 加密 + 认证，不使用 HMAC。

## 核心本质差异总结

1. **只有 HMAC 支持密钥派生（HKDF）**
CMAC/Poly1305/GMAC 只是消息认证，不能把 MAC 原语改装成密钥派生函数。TLS 握手要从 ECDH Z 一值层层导出几十种 secret，这就是为什么握手密钥调度必须 HMAC。
2. **密钥复用模型不同**

- HMAC：同一个密钥 K，可以安全处理成千上万条不同消息。适合握手 traffic_secret，持续对 transcript 做 HMAC 计算。
- Poly1305：每条消息必须换密钥；GMAC：不能重复 nonce。适合 AEAD 每条记录。

3. **性能取舍**

- 有 AES 硬件：GMAC > HMAC > Poly1305
- 无 AES 硬件（嵌入式）：Poly1305 >> HMAC >> CMAC‑AES

## 常见误区

1. ❌：TLS 全部用 HMAC 做完整性。

> 
> 错：记录层密文是 GCM‑GMAC 或者 Poly1305；只有握手 Finished、HKDF 内部才是 HMAC。

2. ❌ Poly1305 可以替代 HMAC。

> 
> 不能，Poly1305 密钥不能复用，无法实现 HKDF 密钥调度。

3. ❌ CMAC 可以拿来实现 HKDF。

> 
> CMAC 基于块密码，没有标准化的 HKDF 等价构造，密码学标准不这么用。

4. ✅ HMAC 的安全根基是哈希；CMAC/GMAC 根基是块密码；Poly1305 根基是有限域数学。
