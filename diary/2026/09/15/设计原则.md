# RESTful API 设计原则

REST（Representational State Transfer，**表述性状态转移**），是 Roy Fielding 提出的一套软件架构风格，不是标准协议，是设计 Web API 的一套思想规范，基于 HTTP 协议，核心是**资源为中心**。

> 
> 核心思想：**一切皆资源**，对资源做增删改查，用 HTTP 方法表达动作，HTTP 状态码表达结果，URL 只描述资源，不描述操作。

## 1. 资源命名：URI 代表资源（名词优先）

- URI 使用**名词**，不要动词，资源是实体
✅ 好：`/users`、`/users/100`、`/orders`、`/orders/20260907`
❌ 坏：`/getUser`、`/deleteOrder`、`/updateUser`（把动作写在路径）
- 复数形式表示资源集合，单数一般不用
- 层级表达从属关系：`/users/100/orders` 用户 100 的全部订单
- 小写，横杠 `-` 分隔单词，不使用下划线、驼峰
- 查询条件放 query 参数，不要塞路径：`/users?page=2&size=20`

## 2. 使用 HTTP Method 表达动作（语义化方法）

表格

| HTTP 方法 | 语义             | 说明                                 |
| --------- | ---------------- | ------------------------------------ |
| GET       | 获取资源         | 查询，只读，不修改服务端数据，可缓存 |
| POST      | 创建资源         | 在集合下新增一条资源                 |
| PUT       | **全量更新**资源 | 完整替换已有资源，不存在则可创建     |
| PATCH     | **部分更新**资源 | 只修改传入的字段，其余保留           |
| DELETE    | 删除资源         | 删除指定资源                         |

示例：

- `GET /users`：获取用户列表
- `GET /users/100`：获取 id=100 用户详情
- `POST /users`：新建一个用户
- `PUT /users/100`：完整覆盖更新用户 100
- `PATCH /users/100`：只修改用户部分字段
- `DELETE /users/100`：删除用户 100

> 
> 注意：不要所有接口都用 POST，丢失 REST 语义。

## 3. HTTP 状态码表达结果，不要全部返回 200

利用标准状态码区分结果，业务错误信息放响应 body。

- 2xx 成功
  - `200 OK`：GET/PUT/PATCH 成功
  - `201 Created`：POST 创建资源成功
  - `204 No Content`：DELETE 删除成功，无返回体
- 4xx 客户端错误
  - `400 Bad Request`：请求参数错误
  - `401 Unauthorized`：未认证，未登录
  - `403 Forbidden`：已登录，但无权限访问
  - `404 Not Found`：资源不存在
  - `409 Conflict`：资源冲突（重复创建）
- 5xx 服务端错误
  - `500 Internal Server Error`：服务器内部异常

❌ 反模式：不管成功失败永远返回 `200`，靠 body 里自定义 `code:0/-1` 判断一切。

## 4. 资源表述：Request / Response 格式

- 主流使用 JSON，统一数据格式
- 返回结构建议统一，包含业务提示、数据：

```json
{
  "code": 0,
  "msg": "success",
  "data": { ... }
}
```

> 
> 严格 REST 不强制自定义 code，但工程实践几乎都会增加业务码。

- **HATEOAS（超媒体作为应用状态的引擎）**
REST 原始约束：返回数据附带资源链接，客户端可以通过链接发现下一步操作。

```json
{
  "id":100,
  "name":"xxx",
  "_links":{
    "self": "/users/100",
    "orders": "/users/100/orders"
  }
}
```

> 
> ⚠️现实业务开发，**绝大多数项目不会完整实现 HATEOAS**，属于理想约束。

## 5. 无状态 Stateless（最重要约束）

> 
> **每一个 HTTP 请求必须包含全部所需信息，服务器不保存客户端会话状态。**

- 服务端不存 session；认证信息（token/jwt）每次请求带上（header: `Authorization: Bearer xxx`）
- 客户端状态保存在客户端，服务器不记忆上一次请求。
- 好处：易于水平扩展，多台服务器可以无差别处理请求。

## 6. 缓存 Cache

利用 HTTP 缓存头 `Cache-Control`、`ETag`、`Last‑Modified`，GET 请求资源可以缓存，减少重复请求。

- GET 查询接口适合缓存；POST/PUT/DELETE 一般不缓存。

## 7. 版本控制

API 迭代需要版本，三种主流方案：

1. URI 路径版本（最常用）：`/v1/users`、`/v2/users`
2. Header 版本：请求头携带 `Accept: application/vnd.myapi.v1+json`
3. Query 参数：`/users?version=v1`（不推荐）

## 8. 分页、过滤、排序、搜索

全部使用 query 参数，不要写进 URL path

- 分页：`/users?page=1&size=20`
- 过滤：`/orders?status=paid`
- 排序：`/orders?sort=create_time,desc`

## 9. 安全

- HTTPS 传输
- 认证：Bearer Token / JWT，放 Header，不要放 URL 参数
- 权限校验，防止越权访问资源

# REST 常见误区（工程踩坑）

1. ❌ URI 写动词 `/getUserInfo`，违背资源为中心
2. ❌ 全部接口只用 POST
3. ❌ 所有响应一律 HTTP 200，靠自定义错误码判断错误
4. ❌ 服务端保存会话状态，破坏无状态
5. ❌ PUT 用来做部分更新（应该用 PATCH）
6. ❌ 过度严格 HATEOAS，业务开发几乎不用

## REST vs RPC

- RESTful：**面向资源**，HTTP method 表达动作，URI 定位资源
- RPC（如 gRPC、传统 `/api/user/update`）：**面向动作 / 函数**，URL 代表调用的方法，参数传进去执行。

> 
> 现实开发很多是 REST‑like：遵循大部分 REST 原则，放弃 HATEOAS，兼顾工程实用性。
