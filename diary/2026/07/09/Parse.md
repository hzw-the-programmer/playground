PostgreSQL 使用一种基于消息的前端/后端协议，其中 **Parse（解析）消息 是 扩展查询协议** 的核心消息之一。与简单的 `Query` 消息一次性发送 SQL 并执行不同，扩展协议将查询过程拆分为 **Parse（解析）→ Bind（绑定）→ Execute（执行）** 等步骤，从而支持预处理语句、参数化查询和更好的性能优化。

---

# 1. Parse 消息的作用

`Parse` 消息告诉服务器：**“请提前分析这条 SQL，将其转换为一个预备语句（prepared statement），但不要执行它。”**

服务器在收到 `Parse` 消息后会执行：

- **词法 / 语法分析**

- **语义分析**（检查表、列是否存在等）

- **查询重写**（根据规则系统）

- 将准备好的语句缓存在会话内，并返回 **ParseComplete** 或 **ErrorResponse**。

一个成功解析的预备语句可以随后被 **Bind**（绑定实际参数）和 **Execute**（执行）多次重用，避免了重复解析的开销。

---

# 2. 消息结构（协议 3.0）

所有多字节整数按 **网络字节序（大端）** 传输。

字段	类型	长度（字节）	说明
消息类型	`char`	1	固定为 `'P'`（ASCII 0x50）
消息长度	`int32`	4	**自身 + 后续所有内容的字节数**（含该长度字段自身）
语句名称	字符串（C风格）	变长，以 `\0` 结束	预备语句的名字。**空字符串 `""` 代表无名语句**
查询字符串	字符串（C风格）	变长，以 `\0` 结束	待解析的 SQL 文本
参数数据类型数量	`int16`	2	后续 OID 数组的元素个数。可为 0
参数数据类型 OID 数组	`int32[]`	数量 × 4	每个参数的预期数据类型 OID。如果未指定则写入 `0`（InvalidOid）

**消息长度 = 4（自身） + 语句名称长度(含\0) + 查询SQL长度(含\0) + 2 + 数量×4**

**示意图**

```text
+------+----------+-----------------+------------------+----------+-----------------+
| 'P'  | 长度(4)  | 语句名 + '\0'   |   SQL文本 + '\0'  | 参数个数  | OID1, OID2 ...   |
+------+----------+-----------------+------------------+----------+-----------------+
```

# 3. 字段详解

## 3.1 语句名称

- 一个以 null 结尾的合法标识符（或空）。

- **命名语句**：客户端自定义名称，如 `"my_stmt"`，在整个会话中存在，直到被 `DEALLOCATE` 或连接关闭。用同名 `Parse` 会覆盖旧的。

- **无名语句**：使用空字符串 `""`（即一个 `\0` 字节）。无名语句只存一个，下一次对无名语句的 `Parse` 会覆盖它。常用于一次性查询。

## 3.2 查询字符串

- 标准 SQL 文本，可包含占位符 `$1`, `$2`... （最高 `$65535`，由参数个数决定）。

- 例如：`SELECT * FROM users WHERE id = $1`

- 字符串同样以 `\0` 结尾。

## 3.3 参数数据类型 OID

- `int16` 指定了后面数组中 OID 的个数。必须与 SQL 中使用的占位符最大编号一致。

- 每个 OID 是一个 `int32`，表示 PostgreSQL 内部类型的 OID（例如 `INT4` 为 23，`TEXT` 为 25）。**0** 表示 “类型未知或由服务器推断”。

- 客户端可以全部填 0，让服务器自己推断参数类型；也可以显式指定 OID 来强制类型转换。例如 `$1::text` 在 SQL 中已能确定，OID 处填 0 也无妨。但如果函数重载或有歧义，可以靠 OID 提示帮助解析器选择。

---

# 4. 服务器响应

Parse 完成后，服务器发回**一条**消息（无长度前缀，直接是类型字节）：

- **ParseComplete**：`'1'`（ASCII 0x31）表示成功。

- **ErrorResponse**：`'E'`，后跟具体的错误字段（严重级别、错误码、消息等）。

连接在收到 `ParseComplete` 之前，**不能再发送其他消息**（除了中断或终止）。成功后，该语句名便可被后续的 Bind/Describe 等引用。
